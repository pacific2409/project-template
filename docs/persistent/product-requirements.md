# Product Requirements Definition

## プロジェクト方針

- 個人開発を通じて技術を学び、仕事での活用につなげたいシステムエンジニアが、取り組む実装課題を決められるプロダクトを目指す。
- 初回Trainでは、開発スタイルで一通りの工程を回せるかの検証を重視する。開発内容をシンプルに保ち、2〜3日、1日8時間（合計16〜24時間）を作業量の目安とする。
- 初回Trainでは、画面・バックエンド・DB・生成AI APIからなる基本的な構成を用いる。具体的な技術は設計で決める。
- アプリケーション、インフラ、デプロイ・公開を含む工程を実施し、作業の再利用と履歴の検証ができる基本的な仕組み化を図る。

## プロダクト概要

### 名称

**DevMenu** - リスキリング駆動開発ツール

### プロダクトタイプ

**Webアプリケーション**

### プロダクトコンセプト

- **学ぶ技術から実装へ**: 学びたい技術・難易度・所要時間・目的を指定し、個人開発やPoCで取り組める課題を見つける。
- **条件を注文して候補を選ぶ**: フォームの入力値をプロンプトテンプレートに組み込み、生成AI APIが提案する複数の課題から取り組む内容を選ぶ。
- **課題を共有して再発見する**: 入力条件と生成された課題を共有履歴に残し、既出の技術名から関連する課題を探せるようにする。

### プロダクトビジョン

システムエンジニアが、仕事で出会った技術や開発作業から学習テーマを見つけたとき、実践する課題まで進めるようにする。
技術習得と仕事での利用前のPoCのどちらにも、使える時間と難易度に合う具体的な課題を提示する。
一度提案された課題は共有履歴から再び見つけられ、次の個人開発の着想にも使える。

### 目的

- 学びたい技術を使った実装課題を提示し、何を作るか決められるようにする。
- 業務での活用を見据えた技術習得や、小さなPoCの題材を見つけられるようにする。
- 既出の課題を共有履歴から探し、再利用できるようにする。

## ターゲットユーザー

### プライマリーペルソナ

- **立場**: 仕事での活用を見据え、新しい技術を個人開発で学ぶシステムエンジニア。
- **背景**: 業務で接したシステムの採用技術・競合技術や、正確さと反復が求められる開発作業の仕組み化に役立つ技術を、学習テーマの起点にする。
- **現在の課題**: 試したい技術はあるが、限られた時間と自分に合う難易度で、何を作れば学習や検証につながるか決めにくい。
- **期待する解決策**: 条件に合う具体的な課題と達成目標を比較し、個人開発やPoCで取り組む内容を決められること。

## 目標・完了条件(Goals)

- 技術・難易度・所要時間・目的を指定し、3件の実装課題と達成目標、学ぶ／検証するポイントを確認できる。
- 入力条件と生成された課題がDBに保存され、技術名を選んで共有履歴から閲覧できる。
- 主要機能を実際にデプロイし、URLを知る人がアクセスできる状態にする。URLの広範な周知や第三者への利用案内は行わず、他者による利用を初回Trainの目的・完了条件としない。
- インフラを含むデプロイ・公開作業に、再利用でき、実施履歴を検証しやすい基本的な仕組みを設ける。
- 安全対策は、合意した基本的な仕組みが意図どおり構成・動作しているかで確認する。個別対策の網羅性、悪意あるリクエストや急激な負荷に対する本番運用水準の備え、恒久的な稼働・運用は初回Trainの完了条件としない。
- 開発スタイルに沿って一通りの工程を実施する。

## 機能要件

### 課題生成条件の入力

**ユーザーストーリー**:
新しい技術を学びたいエンジニアとして、自分に合う実装課題を得るために、学習やPoCの条件をフォームで指定できること。

**受け入れ条件**:
- [ ] 学びたい技術を単語・短い語句で入力できる。
- [ ] 難易度を「初級」「中級」「上級」から選択できる。
- [ ] 所要時間を時間数の数値で入力できる。
- [ ] 目的を「技術習得」「PoC」から選択できる。
- [ ] 任意の「その他の意向」を短文で入力でき、空欄でも注文できる。
- [ ] 送信前に、「その他の意向」に入力した内容がログイン不要の共有履歴で誰でも閲覧できることを利用者に示す。
- [ ] 技術名の入力例と、難易度ごとの目安が表示される。

**設計時に確定する事項**: 所要時間の入力可能範囲（0・負数・小数の扱い）を決め、フォームとバックエンドで同じ基準を用いる。

**優先度**: P0（初回Trainで必須）

### 実装課題の提案

**ユーザーストーリー**:
技術を学ぶ、または仕事で使う前に検証したいエンジニアとして、指定した条件に合う課題を比較し、取り組む内容を選べること。

**受け入れ条件**:
- [ ] フォームの入力値がアプリケーション側のプロンプトテンプレートに組み込まれ、生成AI APIへ送られる。ユーザーが自由記述したプロンプトをそのまま送る方式にはしない。
- [ ] プロンプトで課題を3件に固定し、JSON形式と入力条件への適合を指示する。
- [ ] 1回の注文に対して3件の実装課題を提示する。
- [ ] 生成AI APIの応答をJSONとして読み取り、課題がちょうど3件あることと、各課題のタイトル・概要・達成目標・目的に応じた学ぶ／検証するポイントが空白だけでないことを処理上で確認する。
- [ ] JSONとして読み取れない、課題がちょうど3件でない、または表示に必要な項目が欠ける・空白だけの場合は、設計時に定める有限の試行回数内で再生成する。上限までに有効な3件を得られなければ業務上のエラーとして扱い、提案成功としない。
- [ ] 各課題にタイトル、概要、達成目標が表示される。
- [ ] 目的に応じて、学ぶポイントまたは検証するポイントが表示される。
- [ ] 応答後に提案結果が表示される。生成処理中であることを判別させる表示は初回Trainでは設けない。

**検証方針**: JSONとしての読み取り、件数、表示必須項目の存在と非空は処理上で確認する。課題が入力条件に内容面で適合しているかは、初回Trainでは人が確認する。

**優先度**: P0（初回Trainで必須）

### 課題提案の共有履歴

**ユーザーストーリー**:
既出の技術を調べたいエンジニアとして、保存された課題と生成条件を共有履歴から見つけて閲覧できること。

**受け入れ条件**:
- [ ] 入力条件と、生成された3件の課題がDBに保存される。「その他の意向」が入力された場合、その内容も保存される。
- [ ] JSONの読み取り、課題件数、表示必須項目のいずれかの確認を通過できず業務上のエラーとなった注文は、共有履歴に保存されない。
- [ ] 保存された履歴は、ユーザー登録やログインをせずに利用者が共有して閲覧できる。
- [ ] 履歴に入力された技術名が保存され、既存の技術名を選択肢として表示できる。
- [ ] 技術名を選ぶと、その技術名に該当する履歴と、保存された入力条件・課題を閲覧できる。

**設計時に確定する事項**: 技術名を同じタグとみなす基準（大文字・小文字や前後の空白の扱い）を決め、選択肢の表示と履歴の絞り込みに一貫して適用する。

**優先度**: P0（初回Trainで必須）

### 取り組む課題の選択保存（将来候補）

**ユーザーストーリー**:
個人開発に取り組むエンジニアとして、提案された候補から選んだ課題を後で確認できるように保存できること。

**受け入れ条件**:
- [ ] 提案された課題を選んで保存できる。
- [ ] 保存した課題を後から閲覧できる。

**優先度**: P2（初回Trainの対象外）

### 課題の進捗管理（将来候補）

**ユーザーストーリー**:
個人開発に取り組むエンジニアとして、選んだ課題への取り組み状況を後から確認できるように記録できること。

**受け入れ条件**:
- [ ] 保存した課題に取り組み状況を記録できる。
- [ ] 記録した取り組み状況を後から確認できる。

**優先度**: P2（初回Trainの対象外）

## 非機能要件

### アーキテクチャ

- アプリケーションモジュールはステートレスに設計し、履歴の保存先にはDBを用いる。
- 画面・バックエンド・DB・生成AI APIからなる構成とする。具体的な技術選定は設計で行う。

### ユーザビリティ

- 技術名の入力例と難易度ごとの目安を画面に表示する。
- 初回Trainでは、比較のための追加の表示機能、生成中・失敗時の表示、入力条件を保持した再試行の追加の工夫は設けない。3件の課題を見比べて選ぶ基本的な体験は維持する。

### 信頼性・運用

- 入力条件と生成された課題をDBに保存し、後から共有履歴として閲覧できる。
- インフラを含むデプロイ・公開作業を再利用でき、実施履歴を検証できる基本的な仕組みを設ける。
- 初回Trainでは、恒久稼働や本番運用水準の高負荷対策を完了条件としない。

### セキュリティ

- フォームから受け取る値に基本的な入力検証を行う。
- 生成AI APIの認証情報を利用者のブラウザに公開しない。
- 入力値や生成AI APIから受け取った内容を表示する際、スクリプトとして実行されないように扱う。
- 初回Trainでは生成AI APIの呼び出し回数制限を設けない。将来の導入可能性は排除しない。
- ユーザー登録・管理・ログインは初回Trainでは設けない。悪意あるリクエストに対する本番運用水準の備えや、個別対策の網羅性は初回Trainの完了条件としない。

### パフォーマンス

- 生成結果の応答速度について、初回Trainでは数値目標を設けない。

### 初回Trainの対象範囲

- AIとの相談やチャットによる課題調整は、初回Trainでは行わない。
- 共有履歴の探索は保存済みの技術名から選ぶ方式とし、自由文・全文検索は初回Trainでは行わない。
- 課題の選択保存と進捗管理は将来候補とし、初回Trainでは行わない。
