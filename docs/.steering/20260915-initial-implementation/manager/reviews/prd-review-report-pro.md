## 改善が必要な点

### [推奨] 改善推奨

**R-001**: 同じ技術名として扱う基準が未定義。（Mediumレビューで指摘、今回CLOSE）
- **箇所**: 「課題提案の共有履歴」
- **理由**: 大文字・小文字や前後の空白により、選択肢と絞り込み結果が変わり得る。
- **改善案**: 表記の統一または同一視の基準を、設計で決めて受け入れ条件へ反映する。
- **今回の評価**: PRDに、設計時に基準を確定し選択肢と絞り込みへ一貫して適用する条件が追加された。具体的な同一視の規則は技術・データ設計で決める事項として妥当。

**R-002**: 所要時間の入力可能範囲が未定義。（Mediumレビューで指摘、今回CLOSE）
- **箇所**: 「課題生成条件の入力」
- **理由**: 0・負数・小数の扱いが不明で、フォームとバックエンドの検証が揃わない可能性がある。
- **改善案**: 許可する範囲と整数・小数の扱いを設計で決めて受け入れ条件へ反映する。
- **今回の評価**: PRDに、設計時に範囲を確定しフォームとバックエンドに同じ基準を用いる条件が追加された。具体値の決定を設計に委ねることは妥当。

**R-003**: 生成AI APIが3件未満、形式不正、条件に合わない結果を返した場合の成功判定が未定義。（今回CLOSE）
- **箇所**: 「実装課題の提案」「課題提案の共有履歴」
- **理由**: 「3件提示」「3件保存」を満たせない応答を成功として扱うと、画面と共有履歴が食い違い、受け入れテストの判定も揺れる。
- **今回の評価**: 件数不一致・判定不能時の有限回再生成、上限後の業務エラーと履歴非保存、内容面の人手確認が明記された。ただし、3件と判定できても、タイトル・概要・達成目標・目的別ポイントなど表示必須項目が欠ける応答を成功として保存する余地が残る。
- **改善案**: 3件それぞれに表示必須項目が存在して読み取れることを処理上の成功条件に加え、満たさない場合は件数不一致と同じ失敗扱いにする。課題の妥当性や条件への内容面の適合は、記載どおり人手確認に委ねられる。
- **今回の評価**: JSONとして読み取れること、ちょうど3件であること、各課題の表示必須項目が欠けず空白だけでないことが処理上の成功条件に追加された。失敗時の有限回再生成、上限後の業務エラーと履歴非保存も揃っている。内容面の適合は、初回Trainの範囲に合わせて人手で確認する方針が明確。

**R-004**: 任意の自由入力が全利用者に共有されることを、入力前の利用者にどう伝えるか未定義。（今回CLOSE）
- **箇所**: 「課題生成条件の入力」「課題提案の共有履歴」
- **理由**: 業務に近いテーマを扱うペルソナでは、自由入力に業務上の情報を含める可能性がある。履歴の共有範囲はPRDに書かれているが、入力する本人がその場で把握できる条件はない。
- **改善案**: 「その他の意向」も共有履歴に表示されることを、送信前に分かるようにする受け入れ条件を加える。具体的な文言・画面配置は設計に委ねる。
- **今回の評価**: 送信前の案内が受け入れ条件に追加されている。
