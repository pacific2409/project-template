# Content Guide

## 作成方針
- テンプレートの各項目について `[機能1]`、`[機能2]` や、`[項目1]`、`[項目2]`などが定義されていても、その項目数はあくまで基準であり、本ガイドにおける項目数の指定がない限りは作成の際は実際の要求内容に応じて必要な数だけ項目を追加する。

## 作成における重要なポイント

### 1. 具体性と測定可能性

すべての要件は、その内容や達成条件を判断できる程度に具体的に記述する。測定可能な基準を定義する場合、その項目については、可能な限り客観的に評価できる形で記述する。

**悪い例**:
- システムは高速である必要がある
- ユーザーは使いやすいと感じる

**良い例**:
- コマンド実行時間: 100ms以内(平均的なPC環境で)
- 新規ユーザーが5分以内に基本操作を習得できる(ユーザビリティテストで測定)

### 2. ユーザー中心設計

すべての機能は、明確なユーザーの課題を解決するものでなければならない。

**ユーザーストーリーのフォーマット**:
```
[ユーザー]として、[目的]のために、[機能]ができること。
```

**例**:
```
開発者として、ターミナルから離れずにタスクを管理するために、
CLIから登録・確認・更新を通じてタスクを管理できること。
```

### 3. 優先順位の明確化

すべての機能に優先度を設定する:
- **P0(必須)**: MVP(Minimum Viable Product)に含める機能。これがないとプロダクトとして成立しない
- **P1(重要)**: 初期リリース後すぐに追加すべき機能
- **P2(できれば)**: 将来的に追加を検討する機能


## セクションガイド
テンプレートの各セクションで何を定義するか

### 1. プロジェクト方針
Projectを進めるうえで前提とする方針や、開発において重視する事項を列挙する。

以下のような内容を対象とする。

- Projectで重視する目的や価値
- 開発規模、期間、完成度などに関する方針
- 開発や技術検証において重視する事項
- その他、Project全体の判断に影響する方針


### 2. プロダクト概要

#### 構成要素

1. **名称**: プロダクト名とサブタイトル
2. **プロダクトコンセプト**: 主要コンセプト(最低3つ)
3. **プロダクトビジョン**: 目指す世界観を3-5文で
4. **目的**: 具体的な目的のリスト

#### 例
> **Note:** 以下はあくまで参考例とし、実際の記述は要求に応じて決定する。また、そのような内容・構成とすることを優先する。

```markdown
### 名称
**Devtask** - 開発者向けタスク管理CLIツール

### プロダクトコンセプト
- CLIで完結するタスク管理: ターミナルから離れずにすべての操作を完結
- 優先順位の自動推定機能: タスクの期限、作成日時、ステータス変更履歴などから優先順位を自動推定
- シンプルで高速な操作感: 最小限のキー入力で操作完了、即座のレスポンス

### プロダクトビジョン
開発者がターミナルから離れることなく、効率的にタスクを管理できるCLIツールを提供する。
コマンドラインでの操作に特化し、開発フローを中断させない軽量で高速なタスク管理を実現する。
優先順位の自動推定により、開発者は本質的な作業に集中できる。
```

**具体的な価値提案を含める**

悪い例:
```
便利なタスク管理ツールを作る
```

良い例:
```
開発者がターミナルから離れずにタスク管理できるCLIツール。

提供する価値:
- コンテキストスイッチの削減(GUI↔ターミナルの切り替えゼロ)
- 作業効率の向上(マウス操作不要で平均30%の時間短縮)
- 自動化との連携(シェルスクリプトに組み込み可能)
```

### 3. ターゲットユーザー(ペルソナ)

#### 必須要素

1. **基本属性**: 職業や職種、業務上のポジションなど
2. **背景**: 業務状況や一日のワークフローなど
3. **現在の課題**: 具体的な痛み点
4. **期待する解決策**: どうなりたいか

#### 例

```markdown
### プライマリーペルソナ:
- フルスタックエンジニア
- フリーランスで3-5プロジェクトを並行
- Vim/Emacs + ターミナル環境
- タスク管理に時間をかけたくない
- Markdown、Git、CLIツールを好む
```

### 4. 目標・完了条件(Goals)
Projectによって達成したい目標、およびProjectの完了を判断するための条件を列挙する。

以下のような内容を対象とする。

- Projectを通じて達成したい状態
- Productとして実現すべき状態
- Projectを完了したと判断するために満たすべき条件

> **Note:** 本項では、数値による測定が可能である必要はなく、定性的な目標・完了条件を定義してよい。定量的な指標によって達成状況を評価する場合は、後述の `成功指標(KPI)` として別途定義する。

### 5. 成功指標(KPI)
本セクションの定義・作成は任意とする。

ProductやProjectの成功度合いを定量的に評価するための指標を定義する。

#### SMART原則

- **S**pecific(具体的): 何を測定するか明確
- **M**easurable(測定可能): 数値で測定できる
- **A**chievable(達成可能): 現実的な目標
- **R**elevant(関連性): ビジネス目標と関連
- **T**ime-bound(期限): 達成期限を設定

#### 例

```markdown
### プライマリーKPI
- 日次アクティブユーザー(DAU): 100人(3ヶ月後)
- タスク完了率: 70%以上
- 1日あたりの平均コマンド実行回数: 10回以上
```

### 6. 機能要件

各機能には以下を含める:
- ユーザーストーリー
- 受け入れ条件(チェックリスト形式)
- 優先度(P0/P1/P2)

**フォーマット**:
```markdown
### [機能名]

ユーザーストーリー:
[ユーザー]として、[目的]のために、[機能]ができること。

受け入れ条件:
- [ ] 条件1(測定可能)
- [ ] 条件2(測定可能)

優先度: P0(必須) / P1(重要) / P2(できれば)
```

#### CLIインターフェース

CLIツールの場合、具体的なコマンド例を記載する:

```bash
# 基本操作
devtask add "タスク名" --due 2025-01-15 --priority high
devtask list
devtask next  # 今やるべきタスクを表示
devtask done <task-id>
devtask show <task-id>
```

### 7. 非機能要件

- パフォーマンス
- ユーザビリティ
- 信頼性
- セキュリティ
- スケーラビリティ
について具体的な基準を定める場合は、測定可能な形で記述する。:

**例**:
```markdown
### パフォーマンス
- コマンド実行時間: 100ms以内(平均的なPC環境で)
- タスク一覧表示: 1000件まで1秒以内

### ユーザビリティ
- 新規ユーザーが5分以内に基本操作を習得できる
- ヘルプコマンドで全機能を確認できる

### 信頼性
- データ損失ゼロ(自動バックアップ)
- エラー発生時のロールバック
```

### 8. スコープ外
Productとして明示的に対象外とする機能、要件、対象範囲がある場合に記載する。本セクションの定義・作成は任意とし、該当する事項がない場合は作成しない。

以下のような内容を対象とする。

- Productの目的や性質から、将来を含めて対象としない事項
- Productの責務として扱わないことを明示する必要がある事項
- 実装対象と誤解される可能性があるため、明示的に境界を定めておくべき事項

> **Note:** 現在の開発では実装しないものの、将来的な追加を検討する機能については本項には記載せず、機能要件の優先度によって表現する。
